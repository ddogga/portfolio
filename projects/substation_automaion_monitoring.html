대규모 코드 리팩토링

§02Problem Solving
PS-01조회기능이 데이터, 검색 조건이 늘어날수록 느려지던 문제
문제 상황검색 조건과 데이터가 늘어나면서 조회가 느려짐.
원인
  • 서브쿼리로 컬럼을 가공해 인덱스를 타지 못하는 상태.
  • 문자열 함수 조건이 든 쿼리를, 그 조건이 필요 없는 전체 조회 로직에서도 그대로 사용.
  • 데이터 건수가 늘어날수록 LIKE 절에서 큰 성능 저하 발생.
  • 추가된 검색 조건은 다른 테이블과 조인해서 검색해야 해 조인 비용 발생.
    • 해결 방법
  • 서브 쿼리 가공을 제거하고 코드 단위에서 직접 작업 함.
  • 문자열 매칭을 LIKE 대신 개선: CHARINDEX를 먼저 시도했으나 효과가 없어, RIGHT(da_ref, CHARINDEX('.', REVERSE(da_ref))-1)로 da_ref 끝의 토큰만 잘라 정확히 일치 비교하도록 바꿔 검색 성능을 끌어올림.
  • 추가된 검색 조건은 DB 비정규화로 조인 없이 단일 테이블에서 검색 가능하도록 개선.
  • 문자열 함수 조건의 필요 유무에 따라 실행할 쿼리를 코드 단위에서 분기.
    • 해결 결과2만건 이상의 데이터가 있는 상태에서 3~4개의 검색 조건 조회시 기존에는 15초 이상 걸렸던 로직이 2~3초 이내로 단축 됨.
    핵심 교훈
  • 서브쿼리는 인덱스 활용을 막을 수 있어 성능이 중요하면 지양해야 함.
  • LIKE 같은 넓은 매칭은 데이터가 많아질수록 급격히 느려지므로, 패턴이 정형화돼 있다면 문자열을 잘라 정확히 일치(equality) 비교로 바꾸는 편이 유리함.
  • 조회 성능을 위해서는 조인·정규화 비용과 비정규화의 트레이드오프도 함께 고려해야 함.
    • PS-02대규모 코드 리팩토링
    문제 상황새로운 기능을 추가해야 하는데, 관련 코드가 하나의 클래스 파일에 약 3,000줄 이상 분량으로 구현되어 있어 유지보수에 어려움이 생김.
    해결 방법
  • 여러 곳에 흩어진 중복 코드는 공통 메서드로 분리해 재사용하도록 정리.
  • 각 기능마다 유틸리티 클래스를 따로 만들어 책임을 분산시킴 (예: 데이터 타입 관련 로직을 DataTypeUtils로 추출).
  • 거대한 단일 클래스를 기능·책임 단위로 쪼개, 새 기능은 해당 책임을 가진 클래스에만 손대면 되도록 구조를 개선.
    • 핵심 교훈
  • 하나의 클래스가 너무 많은 책임을 가지면 유지보수와 확장이 급격히 어려워진다. 단일 책임 원칙(SRP)에 따라 기능·책임 단위로 나누는 것이 정말 중요하다고 느꼈다.
  • 중복 제거와 유틸 추출은 단순히 코드량을 줄이는 것을 넘어, 변경 지점을 한곳으로 모아 수정 시 실수와 버그 가능성을 낮춰준다.
    • PS-03JNI를 타는 로직에서 스레드가 무한 대기
    문제 상황여러 요청을 동시에 처리하는 서버에서 워커 스레드 두 개가 무한대기하여 CPU를 100%를 점유하며 멈췄음.
    원인 정확한 원인은 밝히지 못했고, 추측상 아래 두 가지가 원인으로 추정

    1. 비동기 read를 동기처럼 감싼 래퍼가 외부 전력 감시 장비의 응답을 폴링 방식으로 기다리는데, 통신이 직렬 연결 기반인 버퍼에서 동시에 두 스레드가 통신 요청을 보냈으므로 오류 발생

    2. 외부 장비의 문제가 생겨 외부 응답을 받지 못해 스레드가 무한 대기

    해결 방법 연결에 대한 응답이 오지 않을 때 타임아웃을 둬서 스레드가 무한 대기 하는 문제를 방지했다.
    핵심 교훈외부 응답에 의존하는 호출은 반드시 타임아웃을 둬서 스레드가 묶이는 것을 방지 해야함.
