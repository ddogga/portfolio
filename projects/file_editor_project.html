§02Problem Solving
PS-01JPA의 deleteById가 @Version을 무시하는 문제
문제 상황어떤 사용자가 수정중인 데이터를 다른 사용자가 삭제 시 락이 완전히 무시되어 수정-삭제 충돌이 발생.
원인JPA에서 기본으로 제공되는 deleteById 메서드 사용시 기본적으로 삭제 경로에서 버전을 체크하지 않는 동작 특성 때문에 낙관적 락이 삭제에는 적용되지 않았다.
해결 방법수정은 @Version 낙관적 락(충돌 시 ConflictException 409로 재시도 유도), 삭제엔 PESSIMISTIC_WRITE (비관적 락 쓰기 잠금) 과 함께 deleteById를 버전 체크 삭제 쿼리 (`delete ... where id=:id and version=:version) 또는 soft-delete로 교체하고, 중복은 DB UNIQUE 제약으로 최종 방어하며, 서비스 트랜잭션을 readOnly 기본+쓰기만 개별로 분리했다.
핵심 교훈deleteById가 낙관적 락을 우회하듯 ORM 편의 메서드가 안전장치를 건너뛸 수 있으므로 삭제에도 버전 보장이 필요하면 명시적으로 통제해야 하며, 낙관적(편집)·비관적(삭제) 락은 상황에 맞게 나눠 써야 한다.
PS-02예외를 catch 했는데도 트랜잭션이 롤백되는 문제
문제 상황별도 트랜잭션 빈에서 발생한 예외를 잡아 로그만 남기고 정상 흐름을 이어갔는데, 정작 상위 트랜잭션 커밋 시점에 롤백 관련 예외(UnexpectedRollbackException)가 발생했다.
원인예외를 던진 쪽이 별도 트랜잭션 경계를 가진 빈이라 예외 발생 시 트랜잭션이 이미 rollback-only로 마킹됐는데, 호출한 쪽이 try-catch로 catch 구문에서 로그만 남기고 그 예외를 삼키는 바람에 실제 트랜잭션 상태와 예외 흐름이 어긋난 것이 원인이었다.
해결 방법예외를 삼키지 않고 그대로 위로 전파하도록 수정해, 트랜잭션의 롤백 상태와 예외 흐름을 일치시켰다. Propagation.REQUIRES_NEW를 이용해 트랜잭션을 분리한 부분 커밋 방법도 고려해 봤지만, 다중 사용자 환경에서 동시성이슈가 있을 것 같아 전체 롤백 시키는 정책을 채택했다.
핵심 교훈하위 작업에서 실패를 같은 트랜잭션 내에서 삼키는 것은 불가능 하고, 만약 동시성 이슈의 가능성이 있는 상황이라면 데이터 정합성을 위해 전체 롤백 정책을 고려해 봐야 할 수 있다는 것을 배움.
PS-03엔티티 하나 조회에 상위 테이블 10개 이상이 딸려오는 문제
문제 상황여러 엔티티가 부모-자식 관계로 깊게 연결된 트리 구조에서 가장 말단에 있는 데이터 하나만 조회 했을 뿐인데 연결된 상위 부모 엔티티까지 전부 조인 되는 문제 발생.
원인연관관계 기본 설정을 그대로 사용하여 즉시 로딩(EAGER)되고 있었음.
해결 방법연관관계를 지연 로딩(LAZY)로 변경. 연관관계의 데이터가 실제로 필요한 조회에서는 fetch join으로 필요할 때만 데이터를 가져오도록 구현. 지연 로딩만 쓸 때 발생 할 수 있는 N+1 조회 문제를 예방
핵심 교훈연관관계는 기본적으로 지연 로딩으로 두고, 데이터가 실제로 필요한 시점에만 명시적으로 함께 가져오는 것이 좋음.
